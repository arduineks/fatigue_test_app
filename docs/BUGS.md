# Известные баги

Формат: ID, серьёзность, статус, описание, воспроизведение, обходной путь.
Найденные при работе баги добавляются сюда; исправленные переносятся в «Исправлено».

## Открытые

### BUG-15 — после отключения таймер поддержания продолжал тикать и спамил SND FAIL — исправлено 2026-10-08
По логу стенда: в 12:50:24 зафиксировано `DISCONNECTED`, но таймер `maintain_timer`
не был остановлен и каждые 200 мс пытался отправить MOVE — десятки `SND FAIL (нет
подключения)` до 12:51:52. Причина: `disconnect_serial` (`serial_protocol.py`) закрывал
порт и ставил `self.connected = False`, но не трогал активное поддержание. Исправлено:
логика останова поддержания вынесена в единый метод `stop_maintain_force(reason)`
(`traverse_regulator.py`, переиспользуется веткой останова `toggle_maintain_force`),
`disconnect_serial` при `self.maintain_active` вызывает его: таймер остановлен,
`maintain_active=False`, кнопка → «НАЧАТЬ ПОДДЕРЖИВАТЬ», блок траверсы разблокирован,
лог «MAINTAIN: остановлено — нет подключения» (`append_log` + `logger.info`).

### BUG-14 — слепой регулятор на замороженном MID: траверса уводилась в одну сторону — исправлено 2026-10-08
По логу стенда (12:49:35–12:50:24): `control_value` часами стоял на 0.307 N при реальном
MID 0.49 N, ошибка константная — траверса ушла вверх 6.5→15.7 мм. Причина: при
завершении циклов ВНЕ гейта (`cycle_min`/`cycle_max` замораживаются по семантике «вне
гейта — счёт только»), а `cycle_count` растёт и вне гейта. Анти-фриз в `maintain_force_step`
(`traverse_regulator.py`) отслеживал только изменился ли счётчик — он менялся, поэтому
пара MIN/MAX считалась свежей и `control_value = (MIN+MAX)/2` залипал на последнем
цикле внутри гейта. Исправлено: к анти-фризу по счётчику добавлен контроль пары
`(cycle_min, cycle_max)` — при каждом такте пара сравнивается с запомненной, при
изменении обновляется метка `maintain_ctrl_pair_t`; циклы считаются устаревшими, если
НЕ свежа любая из меток (счётчика или пары) дольше `MAINTAIN_CTRL_FREEZE_S = 3.0` с —
тогда `control_value` берётся как среднее мгновенной силы за окно 1 с. Семантику
карточек («вне гейта — счёт только») не меняли. Проверено offscreen-смоуком.

### BUG-13 — регулятор поддержания игнорировал циклы без нажатого START — исправлено 2026-10-08
По логу стенда: при работе «Поддержания силы» без START измерения управляемой
величиной становилось среднее мгновенной силы за 1 с (завышено пиками
вибрации) вместо (MIN+MAX)/2 последнего завершённого цикла — регулятор вёл
траверсу по неверному уровню. Причина: в `maintain_force_step`
(`traverse_regulator.py`) условие выбора `control_value` требовало
`self.measurement_running`, поэтому свежие циклы игнорировались. Исправлено:
условие `self.measurement_running and not cycles_stale and …` → `not cycles_stale
and …` (семантика по докам: есть завершённые циклы и они не протухли 3 с —
управляем MID, иначе окно 1 с). Runtime не проверено (нет PyQt5) — проверить на стенде.

### BUG-12 — выключение «следовать цели цикла» молча обнуляло цель поддержания — исправлено 2026-10-08
По логу стенда: при ВЫКЛ тумблера `on_follow_cycle_target_toggled`
(`main_window.py`) ветка ВЫКЛ без проверки восстанавливала прежнее значение цели;
при прежнем «0» активный регулятор мгновенно ретаргетировался на 0 Н
(в логе: target 0.330 -> 0.000, MOVE вниз 1.4 мм/с). Исправлено: прежнее
значение восстанавливается только если оно валидно и > 0 (с `logger.info` и
`append_log` «MAINTAIN: цель из follow-off … N»); если оно невалидно/равно 0/
отсутствует — `maintain_target_n` НЕ меняется, в поле показывается текущая цель
через `_n_to_maintain_units`, пишется предупреждение «прошлое значение цели
некорректно — цель поддержания сохранена». Проверено offscreen-смоуком.

### BUG-11 — запись велась в одну и ту же папку: привязка к START + неуникальное имя — исправлено 2026-10-07
По логу стенда: сессия записи стартовала только по кнопке START измерения,
а оператор ведёт осцилляцию через «Поддержание силы» без START — запись либо
не стартует после перезапуска приложения, либо копится в одной папке.
Дополнительно: два старта записи в одну секунду давали одинаковое имя папки,
и `mkdir(exist_ok=True)` молча переиспользовал старую (дозапись в тот же
data.csv). Исправлено: кнопка «СТАРТ ЗАПИСИ / СТОП ЗАПИСИ» в верхней строке
(ручная запись без измерения, elapsed от старта записи), START измерения
сначала завершает активную сессию и всегда создаёт новую папку, имя папки
гарантированно уникально (суффикс _2, _3, …). Проверено offscreen-смоуками.

### BUG-10 — строки таблицы циклов в PDF рисовались в одну строку — исправлено 2026-10-07
В `_draw_report` (session_recorder.py) цикл отрисовки строк таблицы
«Данные за последние 30 секунд» не увеличивал `y` после строки — все строки
рисовались поверх первой. Найдено при ревью кода этапа 0 (самописный

### BUG-9 — MAX/MIN занижены относительно пиков синусоиды («лесенка сверху») — исправлено 2026-10-07
По логу стенда: детектированный MAX ниже реального пика на ~0.014–0.024 N при
амплитуде 0.084 N (до 30% кривой остаётся выше линии MAX). Причина: dead-band
скип (`abs(delta) < tolerance*0.15`) пропускал кадры целиком, а у пика подъём
за кадр меньше dead-band — candidate замирал ниже настоящего пика. Исправлено:
трекинг экстремумов перенесён ДО dead-band скипа + подтверждение перегиба по
величине отката (>= tolerance от кандидата) вместо 2 кадров против направления.
Проверено симуляцией на логе: недобор 0.014 → 0.0002 N.

### BUG-8 — карточки MIN/СРЕДНЕЕ/МАКС «замирают» при спуске траверсы — исправлено 2026-10-07
При однонаправленном перемещении траверсы (спуск 9→2 МПа) циклы не завершаются
(нужен пересечение MID вверх), поэтому карточки держали последний завершённый
цикл (3–4 МПа), пока график уходил вниз. Исправлено: гейтинг по скорости
траверсы — при макро-перемещении (|v| > 0.05 мм/с) анализ циклов приостановлен,
карточки показывают живые экстремумы потока; после остановки состояние анализа
сбрасывается и MID заново учится на новом уровне. Runtime не проверен (нет PyQt5).
### BUG-7 — фриз при переключении на вкладку лога (серьёзность: высокая) — исправлено 2026-10-07

Runtime не проверено (нет PyQt5 на этой машине) — проверить на стенде.

### BUG-1 — Возможная потеря измерительных кадров при активности UI (серьёзность: средняя)
Опрос serial QTimer'ом каждые 5 мс при кадрах ~3 мс: при загрузке GUI-потока
(перерисовка графика, меню) кадры могут теряться или опаздывать. Пика скорости не видно,
но длинные записи могут «замирать» на время перерисовки 300k точек.
**Обходной путь:** уменьшать окно истории (X-scale) на длинных записях.
**Связь:** TD-1, TD-3.

### BUG-2 — Битый кадр принимается как валидный (серьёзность: средняя)
Нет CRC и проверки диапазонов: кадр, случайно совпавший маркерами 0xAA/0xBB,
даёт выброс силы/позиции на графике и может сбить анализ циклов.
**Обходной путь:** визуально отфильтровать выбросы; перезапуск измерения.
**Связь:** TD-2.

### BUG-3 — Очистка графика до подтверждения START (серьёзность: низкая)
`send_start` очищает график/буферы сразу при отправке `START_YYY`; если устройство
не ответит `START_OK_YYY`, данные сброшены, а измерение не началось.
**Связь:** TD-2.

### BUG-18 — GUI-фриз на часы во время оценки циклов: битый кадр без CRC → inf/NaN → шкала Y уходит в inf (исправлено 2026-10-27)
Симптомы стенда: через ~1–1.5 ч работы GUI «висит» (кнопки активны, но
график/счётчики не обновляются), ядро отрисовки 100%, RAM стабильна
(~300 МБ), лечится отключением/подключением STM, потом повторяется.
Цепочка: CRC в протоколе нет (известное ограничение) → при ошибке
передачи float32 поля кадра дают мусор (вплоть до inf/NaN) →
`update_y_scale`: `math.ceil(inf)` = `OverflowError` (каждый paintEvent
падает — график перестаёт перерисовываться, GUI жив) или `ceil(1e30+...`
→ y_max гигантский → цикл сетки `while value <= force_max: value += 0.5`
в `_paint_content` крутится ~2·10⁹ итераций — GUI-поток 100% (ядро
отрисовки!). Disconnect очищает буферы → восстановление. Порядок
значений совпадает с наблюдениями.

Исправление (несколько уровней защиты):
1. Валидация полей кадра в `process_measurement_frame` и в пайплайне
   (`_on_frame`): force/mm/raw/filtered должны быть конечными и в
   разумных диапазонах (±10 кН, ±1000 мм, int32) — битые кадры
   отбрасываются, серия пишется CRITICAL в лог (P1.3).
2. Санитизация шкалы в `update_y_scale`: если min/max окна не конечны —
   шкала фиксируется 0..1, CRITICAL в лог.
3. Предохранители в трёх циклах сетки `_paint_content`: максимум 4000
   итераций и проверка isfinite границ — даже при протечке мусора
   дальше paint не зависает.
4. SerialWorker: busy-guard — серия «мгновенных» пустых чтений
   (<2 мс) вызывает sleep (защита от выкрутившегося таймаута чтения
   на некоторых драйверах; GUI при этом жив — второй кандидат на
   тот же симптом).

Проверено headless: inf/NaN кадры отбрасываются (валидация), нормальный
кадр проходит; update_y_scale с inf/NaN → 0..1 без исключений; нормальная
шкала не тронута. Поведение на стенде не проверялось.

### BUG-16 — FORCE_N тормозил (ядро 100%): связная min/max-огибающая рисовалась через drawPolyline (исправлено 2026-10-12)
Фидбек стенда: при включении отображения FORCE_N график начинал тормозить,
ядро в 100%. Воспроизведено offscreen (ForceGraphWidget, 900×500, 72k кадров
при 600 SPS, окно 120 с): полный `grab()` с FORCE_N — ~268 мс (без FORCE_N —
~7 мс). Причина: регрессия коммита `3a744aa` («возврат „линий“ вместо
pointcloud») — в ветке децимации min/max по пиксельным столбцам две
огибающие (верхняя max и нижняя min) стали рисоваться связной полилинией
`painter.drawPolyline(QPolygonF)`. При `width>1` и включённом Antialiasing
растеризатор Qt обводит такую полилинию одним составным контуром со склейкой
сегментов (stroke join) — на «расчёске» (много отсчётов на столбец: при окне
120 с это ~89) штрих-перекрытие даёт квадратичный перерасход: ~490–585 мс на
одну огибающую из ~805 точек, тогда как те же связные отрезки через
`drawLines` — ~5 мс. (drawPath с той же геометрией — тоже ~490 мс; при
`width=1` полилиния внезапно быстра, поэтому RAW/FILTERED страдали слабее
FORCE_N с `width=2`.) Исправлено:
- огибающие рисуются последовательными отрезками `drawLines` (QLineF
  между соседними столбцами) вместо `drawPolyline` — тот же видимый результат
  (непрерывная линия), визуальная эквивалентность подтверждена пиксельным
  диффом и просмотром снимков;
- окно данных конвертируется в numpy-массив ОДИН раз на paint и
  переиспользуется (`_np_window`): раньше `values[start:end]` 72k
  конвертировался отдельно в `update_y_scale` и `draw_signal` (~3.5 мс каждый);
- min/max окна для границ шкалы и диапазонов RAW/FILTERED считаются numpy
  (`_np_minmax`) вместо двух Python-проходов по списку.
Замер offscreen (медиана `grab()`, 50 прогонов): FORCE_N при окне 120 с
268 → ~13 мс; при окне 5 с ~17–29 → ~8 мс; RAW/FILTERED при 120 с ~24 → ~13 мс.
Логика (данные, карточки, регулятор, детекция циклов) не менялась; UI не
тронут. Верифицировано: offscreen-замеры до/после, пиксельный дифф снимков,
MainWindow offscreen smoke, проверки эквивалентности numpy/Python min/max.

### BUG-12 — Удлинение в PDF-отчёте считалось неверно (исправлено 2026-10-09)
В PDF-отчёте удлинение показывалось −0.319 при фактических 45.695
(сессия Образец-1_08-10-2026_15-28-54) и 55.440 (последние сессии
09-10-2026). Причина: `build_stats_rows` (measurement_session.py) считал
удлинение как `база − позиция`, где «база» — позиция траверсы после
100 циклов (`elongation_base_mm`, коммит 91b1f4f). Позиция траверсы в
отчёте — абсолютная координата от нуля, поэтому «база после 100 циклов»
давала (55.122 − 55.440) = −0.319. Исправлено:
- база удлинения = 0 (нуль координаты траверсы в начале испытания);
- удлинение = `позиция − база` (знак исправлен);
- удалена бессмысленная строка «База (позиция после 100 циклов), мм».
Верифицировано на реальных data.csv сессий (45.695 / 55.440) и
парсингом сгенерированного PDF (pdftotext).
